# RSS取得・公開再表示の一時停止

2026-11-11。提供元の商用利用条件の確認が完了していないため、独自解説13記事を中心に運営する構成へ変更する。AdSenseの承認や権利問題の解消を保証するものではない。

## 停止する箇所

- トップページ: RSS一覧、検索・絞り込み、取得・採点表示のJavaScriptを公開HTMLから外す。news.jsonもフィードもブラウザから取得しない。`#news`は記事や既存ナビゲーションからの移動先として残し、自作の案内文とNHK・BBC日本語・Googleニュースの公式サイトへのリンクを表示する。
- SEO: トップのtitle、description、OG title/descriptionを金融・暗号資産の独自解説中心の実態に合わせる。canonical・OG URL、13記事、記事一覧生成マーカー、サイトマップ、記事の内部リンクを維持する。
- 自動取得: `.github/workflows/news.yml`からscheduleを外し、残すworkflow_dispatchのジョブも固定のfalse条件で実行させない。旧cronは `7 */3 * * *`。変更を戻すだけで無断再開しない。
- 公開JSON: ソースの`data/news.json`は見出しなし・articles空のpaused状態に置き換える。Pagesの許可リストからニュースJSONを外し、ステージング先を毎回作り直す。次回公開後はPagesの`/data/news.json`へファイルを配信しない（404を確認する）。
- 公開のトリガー: Pagesのworkflow_run対象からRSS更新を外す。独自記事ビルド後の公開と既存の手動公開手段は維持する。今回の作業でmainへのマージ・公開は行わない。

取得・採点スクリプト`update_news.py`とそのオフラインテストは変更せず保持する。旧RSS UIのHTML断片・JavaScriptは`scripts/rss-ui.fragment.html`にデータなしで保管する。scripts配下はPagesに公開しない。停止状態のままプログラムを手動実行することは技術的には可能なので、許諾確認前にライブ取得を実行しない。

## 反映前と反映後の違い

PRの作成だけでは、既存のmain上のスケジュールや現在の公開サイトは変わらない。追加取得を止めるため、GitHub上の既存RSS更新workflowを無効化する運用を併用する。これはmainファイルの書き換え・公開ではない。停止時にRSSの実行中・待機中ジョブがあれば、それらも対象を確認して停止する。記事ビルド・Pages等の別workflowは停止しない。

公開サイトの一覧とJSONの配信停止は、ユーザー確認後のマージとPagesデプロイで初めて有効になる。それまでは既存の公開ページやJSONが引き続き取得できる可能性がある。即時の公開停止を優先する場合は、別途ユーザーの指示で緊急デプロイまたは公開停止を検討する。

## 見出しデータが残る場所と調査結果

| GitHub Pagesの現行サイト・JSON | 次回公開の成果物からJSONを除外し、RSSの再表示を停止する構成を検証 | 承認後デプロイし、一覧がないこととJSONの404を確認。キャッシュが残る場合は配信元の更新・保持状況を確認 |
| Git履歴 | ベースmain ecba5fbまでの履歴でnews.jsonに関係するコミットが142件 | 空JSONへの置換では過去コミットは消えない。旧コミットURL・Raw・ブランチ・PR参照から取得できる可能性がある |
| 旧HTML複製・配布ZIP | リポジトリ内に旧実装を含む。ZIP内news.jsonはarticles空・not_startedだった。Pages許可リストには含めない | 旧HTML本文に別の転載対象がないか、権利判断を要する場合は追加点検する |
| Actionsの既存Pages成果物 | 調査時に未期限切れgithub-pages成果物が複数存在。過去の公開処理はnews.jsonを同梱していた | データを含み得る過去成果物の削除、保持期間、旧公開内容・キャッシュを別途判断。今回は削除しない |
| ローカルclone、fork、キャッシュ等 | 今回の変更では制御できない | 必要時は保存先ごとに対応。履歴削除でも第三者コピーの消去は保証できない |

履歴・成果物を権利上問題のないものと認定したわけではない。権利者との確認で削除が必要になった場合は、対象のコミット・パス・ブランチ・タグ・PR参照・成果物を特定し、バックアップと影響を説明したうえで、履歴書き換えやGitHubへのキャッシュ等の削除相談を別途承認してもらう。今回はforce push、履歴の書き換え、過去成果物の削除、リポジトリの削除は行わない。

## 再開前の条件と手順

1. NHK、BBC日本語、Google News各フィードと原発行元の利用条件を確認する。広告付きサイト、見出し・メタデータ再表示、発行元名の分離・並べ替え、取得頻度、保存期間、Git履歴での継続公開、出典・リンクの条件を含める。必要な許諾を得て記録する。
2. このPRの親コミットや保存したUI断片から必要な構成を確認し、再開専用PRを作る。取得許諾のない提供元は再開対象にしない。過去のnews.jsonをそのまま戻さず、許諾した範囲で新方式のデータを作る。
3. トップUI・ブラウザ取得、公開JSONの許可リスト、RSS workflowの実行条件・cron、必要ならPagesの連動を個別にレビューする。記事主体の構成とSEOは維持する。
4. 全テスト・保存データの点数検算・ブラウザ表示・障害時の挙動を確認してユーザーが承認する。マージ前にworkflowを有効化しない。mainに許可済み構成が反映されてから、無効化したRSS workflowを有効に戻す。
5. 既存RSSプログラムの失敗時の旧スナップショット保持は、許諾の保存期限と整合するか再検討する。3時間更新や72時間の選定条件は、Git履歴に残る期間の上限を意味しない。

## テスト

`python -m unittest discover -s tests -v`はライブRSSを取得せず、既存の取得・採点・障害時保持を検証できる。停止の追加テストではcronなし・手動ジョブ停止・空JSONに加え、Pagesの実際のステージングコマンドを実行し、以前のnews.jsonがある成果物フォルダでも除去されることを確認する。

ブラウザではデスクトップ・スマートフォン幅で13記事・公式サイト案内・停止表示を確認し、ニュースJSONや外部RSSへの通信がないこと、公開成果物にnews.jsonや保存UIがないことを検証する。テスト目的でライブ取得は再開しない。

## 今回の運用結果・検証結果

- GitHub上の`Update news RSS`を無効化し、APIで`disabled_manually`を確認。確認時点で直近のRSS実行履歴に実行中・待機中のジョブはなかった。記事ビルドとPagesのworkflowは無効化していない。
- 全136テスト通過。既存の取得・採点テストはオフラインで維持。
- 実際のPagesステージングを行った成果物をローカル配信し、1440/390/320px幅で表示、13記事と固定3ページのリンク、`#news`移動先を確認。JSON/RSS/外部サイトへの自動通信、ページ全体の横はみ出し、JavaScriptエラーなし。
- このローカル成果物では`/data/news.json`と`/scripts/rss-ui.fragment.html`は404。これは本番への配信停止が完了したという意味ではない。本番はユーザー承認後のデプロイで確認する。
- 記事13本、サイトマップ、robots.txt、記事生成・RSS採点のPythonプログラムはベースmainから変更なし。Git履歴を書き換えず、新しいブランチ・ドラフトPRでレビューする。
